# Deployment Walkthrough

Step-by-step guide for deploying AWS infrastructure generated by terraform-builder.

## Prerequisites

- AWS account with admin access
- GitHub repository for your project
- AWS CLI configured (`aws configure`)
- Terraform 1.14+ installed
- GitHub personal access token (for bootstrap)

## Workflow Execution Order

Workflows must be run in this exact order:

```
0.1  →  0.2  →  1  →  2  →  3
one-time    one-time    repeat  repeat  repeat
```

### Step 1: Provision Terraform Backend (Workflow 0.1)

**Purpose:** Creates the S3 bucket and DynamoDB table for Terraform state.

1. Navigate to **Actions** → **0.1 — Onetime Provision Terraform Backend**
2. Click **Run workflow**
3. Fill in:
   - `bucket_name`: `<project>-terraform-state` (e.g., `my-app-terraform-state`)
   - `table_name`: `<project>-terraform-lock` (e.g., `my-app-terraform-lock`)
4. Click **Run workflow**

**What it creates:**
- S3 bucket with versioning and encryption
- DynamoDB table with `LockID` partition key

> **Note:** You need AWS credentials configured. For the first run, use IAM access keys. After workflow 0.2, OIDC will be available.

### Step 2: Bootstrap CI Role and GitHub Secrets (Workflow 0.2)

**Purpose:** Creates the GitHub OIDC IAM role and populates GitHub environment variables/secrets.

1. Navigate to **Actions** → **0.2 — Onetime Provision GitHub OIDC Secrets Variables**
2. Click **Run workflow**
3. Fill in:
   - `github_token`: Your GitHub PAT with `repo` and `admin:org` scopes
   - `aws_account_id`: Your 12-digit AWS account ID
   - Other fields use defaults based on your config
4. Click **Run workflow**

**What it creates:**
- IAM OIDC identity provider for GitHub Actions
- IAM role (`<project>-ci-role`) with scoped policies for your enabled services
- GitHub environment variables (per environment): `AWS_REGION`, `PROJECT_NAME`, VPC CIDRs, RDS settings, ECS settings, etc.
- GitHub repository-level variables: `TF_STATE_BUCKET`, `TF_STATE_DYNAMODB_TABLE`
- GitHub secret: `CI_AWS_ROLE_ARN`

### Step 3: Deploy Infrastructure (Workflow 1)

**Purpose:** Runs `terraform plan` and `terraform apply` for a chosen environment.

1. Navigate to **Actions** → **1 — Deploy Infrastructure**
2. Click **Run workflow**
3. Select the **environment** (e.g., `staging`)
4. Click **Run workflow**

**What it does:**
1. Assumes the OIDC role
2. Exports all GitHub environment variables as `TF_VAR_*`
3. Runs `terraform init` with S3 backend config
4. Runs `terraform plan` and uploads the plan to S3
5. Runs `terraform apply`

**Created AWS resources** (depends on your config):
- VPC, subnets, route tables, internet gateway
- Security groups
- RDS PostgreSQL instance
- ECS cluster, task definition, service
- ALB with HTTPS listener
- ECR repository
- KMS key
- Secrets Manager secrets
- SSM parameters
- Route53 DNS records
- And more...

### Step 4: Build and Deploy Backend (Workflow 2)

**Requires:** ECS enabled in your config.

1. Navigate to **Actions** → **2 — Backend Build and Push**
2. Click **Run workflow**
3. Select the **environment**
4. Click **Run workflow**

**What it does:**
1. Waits for workflow 1 to be healthy (cross-workflow check)
2. Logs into ECR
3. Builds Docker image using your framework-specific Dockerfile
4. Pushes to ECR with `latest` and commit SHA tags
5. Forces new ECS deployment
6. Waits for ECS service to stabilize

### Step 5: Deploy Frontend (Workflow 3)

**Requires:** Frontend enabled in your config.

1. Navigate to **Actions** → **3 — Frontend Deploy**
2. Click **Run workflow**
3. Select the **environment**
4. Click **Run workflow**

**What it does:**
1. Waits for backend workflow to be healthy
2. Installs Node.js dependencies
3. Writes `.env.production` with API URL and CDN URL
4. Runs `npm run build`
5. Syncs build output to S3 with cache-control headers
6. Invalidates CloudFront distribution

## Environment-Specific Configuration

After initial setup, you can customize per-environment settings by editing GitHub environment variables:

| Variable | Description | Example |
|----------|-------------|---------|
| `AWS_REGION` | Deployment region | `us-west-2` |
| `PROJECT_NAME` | Project identifier | `my-app` |
| `RDS_INSTANCE_CLASS` | Database size | `db.t4g.small` |
| `ECS_TASK_CPU` | Container CPU | `512` |
| `ECS_TASK_MEMORY` | Container memory | `1024` |
| `ACM_CERTIFICATE_ARNS` | SSL certificates | `["arn:aws:acm:..."]` |
| `ROUTE53_ZONE_NAME` | DNS zone | `example.com` |

## Destroy and Recreate

### Destroying Infrastructure (Workflow 4)

Use when you need to tear down non-persistent resources (e.g., cost savings in non-prod).

1. Run **4 — Destroy Infrastructure Keep RDS**
2. Enter the environment name as confirmation
3. Workflow preserves: VPC, RDS, ECR, KMS
4. Workflow destroys: ECS, ALB, Lambda, DynamoDB, Route53 records

A state snapshot is saved to S3 before destruction.

### Recreating Infrastructure (Workflow 5)

Restores previously destroyed infrastructure.

1. Run **5 — Recreate Infrastructure**
2. Select the environment
3. Workflow restores the pre-destroy state snapshot
4. Runs `terraform plan` and `terraform apply`

> **Prerequisite:** Workflow 4 must have been run first (creates the state snapshot).

## Verifying Deployment

### Check ECS Service

```powershell
aws ecs describe-services `
  --cluster <project>-<env>-cluster `
  --services <project>-<env>-service `
  --region <region>
```

### Check ALB Health

```powershell
aws elbv2 describe-target-health `
  --target-group-arn <target-group-arn> `
  --region <region>
```

### Check RDS Connectivity (via Bastion)

```powershell
# If EC2 bastion is enabled
aws ssm start-session --target <instance-id> --region <region>

# Then on the bastion:
psql -h <rds-endpoint> -U postgres -d appdb
```

### Check API Health

```powershell
Invoke-RestMethod "https://<api-domain>/<project>-<env>/api/v1/health"
```

## Cost Optimization

- Use the **Lambda scheduler** to stop EC2 + RDS outside business hours
- Set `ecs_service_desired_count=0` in non-prod to pause containers
- Use `db.t4g.micro` for non-prod and `db.t4g.small` or higher for prod
- Run workflow 4 to destroy non-persistent resources when not needed
